# Claude Code向け指示書: Rockhopperオペロン予測の実装(Phase 6f、`genomic_context`への統合)

## 位置づけ

これは**実装指示書**です(これまでのPhase 6c/6d/6e調査指示書とは違い、
実際のコード変更・コミットを行うフェーズ)。Phase 6a(STRING)のM1-M5と同じ
「各マイルストーンごとに1コミット、テストを緑に保つ」進め方に倣う。

設計判断の根拠は`claude/phase6_external_evidence_design.md`のPhase 6e
セクション(および今回の追加検証セクション)に記録済み。要点だけ以下に
再掲する。

## 設計判断

### 1. カテゴリ・コンポーネント

新コンポーネント**`rockhopper_operon`**を、既存の**`genomic_context`
カテゴリ**に追加する(`string_neighborhood`と同じ場所、同じ枠を共有)。
新カテゴリは作らない — Phase 6aの決定2と同じパターン。

### 2. 非対称な扱い(最重要の設計判断)

検証の結果(Phase 6e追加検証、LK57/LK51サンプル・3段階のリード数)、
Rockhopperが「同一オペロンとしてマージしなかった」ことは、発現量不足では
説明できず、**Rockhopper内部の近接カットオフ(遺伝子間gapがおよそ30〜70bp
を超えると同一転写単位と判定されなくなる)による手法的な見落としの可能性が
高い**と判明している。したがって:

- ペア(query, candidate)が**Rockhopperの予測で同一オペロン(転写単位)に
  含まれる** → **陽性シグナル**として加点する。
- ペアが同一オペロンに含まれない(マージされなかった) → **`MISSING`
  として扱い、加点も減点もしない**(STRING cooccurrence/neighborhoodの
  「評価済みゼロ」`AVAILABLE, normalized_value=0.0`とは意図的に異なる
  扱い。STRINGは生物種全体で系統的に計算されているため「評価済みゼロ」が
  妥当だが、Rockhopperは内部カットオフによる偽陰性の実例(Mtp)が既に
  確認されているため、「マージされなかった」を陰性の証拠として使うのは
  誤り)。
- 両タンパク質のいずれかが、そもそもどの精度計算済みサンプルの転写単位
  モデルにも登場しない(発現がなさすぎて転写単位として認識されなかった
  場合等)は、同じく`MISSING`として扱う。

### 3. 複数サンプルにまたがる集約

異なる増殖条件で同じオペロンでも検出されたりされなかったりすることが
Mtpの件で分かっている(条件依存の可能性は否定されたが、Rockhopperの
近接カットオフ問題とは別に、真に条件依存で転写されるオペロンも存在し
うる)。そのため、**複数サンプル(条件)でRockhopperを実行し、いずれか
1サンプルでも同一オペロンとして検出されればそのペアは陽性**とする
(OR集約)。単一サンプルだけに頼らない。

### 4. 事前計算・キャッシュ方式(重要: オンザフライ実行はしない)

Rockhopper自体の実行は高速(1回20〜49秒)だが、FASTQ取得がボトルネック
(GB級のダウンロードが必要)。STRING(Phase 6a decisions 6)と同様、
**「一度だけ計算してキャッシュする」**方式にする。スコアリング実行時に
Rockhopperを毎回起動することはしない。

具体的には:

1. 代表的な複数サンプル(最低4サンプル程度を推奨: GSE77738から酢酸・
   メタノール・トリメチルアミンの各条件を1つずつ、GSE64349から硫黄化合物
   条件を1つ)についてFASTQを取得し、Rockhopperを実行する。今回の検証で
   使ったような間引きリード(10万リード等)ではなく、可能な範囲でフル
   リード(または少なくとも数百万リード規模)を使うことを推奨する
   (検出感度を上げるため。ネットワーク帯域に応じて現実的な範囲で判断
   してよい)。
2. 各サンプルの`_operons.txt`(またはRockhopperの該当出力)から
   「同一転写単位に属する`old_locus_tag`のグループ」を抽出し、サンプル
   ごとに正規化したJSON(例:
   `[{"sample": "LK57", "condition": "acetate", "operon_groups": [["MA_3896","MA_3897","MA_3898","MA_3899"], ...]}, ...]`)
   として1つのキャッシュファイルにまとめる。STRINGのbulkファイルと同様、
   このファイルを`core/cache.py`とは別に(生データそのものなので)
   リポジトリ内の適切な場所(例: `data/cache/rockhopper_operons.json`)に
   保存し、以後はこれを読むだけにする。
3. 元のFASTQ・Rockhopper実行環境自体はサイズが大きいため、`.gitignore`
   済みの`data/temp/`配下に置いたままでよい(コミット不要)。今回の調査で
   既に`data/temp/rockhopper_investigation/`に一式残っている場合は再利用
   できるか確認すること。

### 5. Interaction_Evidence_Detailでの表示

STRING同様、どのサンプル・条件で同一オペロンとして検出されたかが分かる
形で明細に残す(例: `rockhopper_operon: detected (sample=LK57, condition=acetate)`)。
`MISSING`の場合も「未検出」であって「陰性」ではないことが分かる表現に
すること(既存のMISSING表示の慣習に合わせる)。

### 6. 帰属表示

Rockhopper自体の引用([PMC6776731](https://pmc.ncbi.nlm.nih.gov/articles/PMC6776731/))
をSTRING(CC BY 4.0)・GEO(Phase 6b)と同様、Indexシート/ドキュメントに
追加する。ライセンス・利用条件を軽く確認し、記載すること。

## 実装マイルストーン(各ステップごとに1コミット、テスト緑を維持)

- **M1**: 代表サンプル(4サンプル程度)のFASTQ取得 + Rockhopper実行 +
  結果を正規化したキャッシュファイル(`data/cache/rockhopper_operons.json`
  相当)の生成。生成に使ったスクリプト(`.ptt`/`.rnt`変換を含む)は
  `analysis/rockhopper_operon_bridge.py`としてリポジトリに残す(今回の
  調査で作った`claude/genbank_to_ptt_rnt.py`を再利用・格上げしてよい)。
  このマイルストーンの出力(キャッシュJSON)自体はコミット対象(小さい
  はず)。生FASTQ・Rockhopper本体はコミットしない。
- **M2**: `rockhopper_operon`コンポーネントを`genomic_context`カテゴリに
  追加。キャッシュJSONを読み、ペアのMISSING/陽性判定を行うルックアップ
  ロジックを実装。Cap値は暫定でよい(STRING同様、暫定である旨をコード
  コメント・ドキュメントに明記)。
- **M3**: `legacy_additive`フォローアップ(Phase 5・Phase 6aのM4と同じ
  パターン)。
- **M4**: `Interaction_Evidence_Detail`に新コンポーネントを反映、帰属
  表示追加、実データでの検証(既知の3複合体 Mcr/Nif/Mtp を使い、Mcr/Nifが
  陽性・Mtpが`MISSING`(陰性ではなく)として正しく表示されることを確認)。

## ついでに対応してほしいこと(小さな修正)

- `analysis/interaction_scoring.py`のコードコメントに残っている可能性が
  高い「MA_3898=NifK, MA_3899=NifD」の誤りを、正しい「MA_3898=nifD,
  MA_3899=nifK」に訂正する(Phase 6eの調査で判明済み)。
- 今回の調査で作成した`claude/phase6e_rockhopper_lk57_validation.md`
  (追加検証レポート)・変換スクリプトをコミットしておく(このPhase 6f
  実装の直接の根拠であるため、実装と一緒にコミットしておくと後から
  経緯を追いやすい)。

## 非対応・スコープ外

- GSE77738全61サンプル・GSE64349全15サンプルを網羅したキャッシュ生成は
  不要。代表的な数サンプルで十分(条件横断的なOR集約という設計自体が、
  全サンプル網羅の必要性を下げている)。
- Rockhopperの近接カットオフの正確な値(30〜70bpのどこか)を特定する
  作業は不要。非対称設計(マージ失敗=MISSING)により、正確な値を知らなくても
  正しく動作する設計にしてある。
